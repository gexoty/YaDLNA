# Диагностика и известные ограничения

Сначала читать состояние. Не менять Quasar, ALSA или системные библиотеки для подавления предупреждений.

## Обнаружение

ПК/телефон и колонка должны быть в одной доступной локальной сети. Проверить AP/client isolation, VPN и разрешение приложению работать в частной сети Windows. SSDP: UDP 1900 multicast; HTTP управления: TCP 49494. Проверить в браузере `http://IP_КОЛОНКИ:49494/description.xml`. Если XML доступен, а списка устройств нет, проверить multicast/контроллер.

## Нет звука

```powershell
adb shell cat /run/station-dlna/receiver.log
adb shell cat /run/station-btproxy/proxy.log
adb shell ps
adb shell cat /proc/asound/card0/pcm0p/sub0/status
adb shell cat /proc/asound/card0/pcm0p/sub0/hw_params
```

Версию смотреть в ADB shell:

```sh
LD_LIBRARY_PATH=/system/vendor/quasar/libs:/system/vendor/quasar:/lib:/usr/lib /data/opt/station-dlna/bin/station-dlna --version
```

- Нужна версия 0.1.1: в 0.1.0 HTTPS не работал из-за отсутствующего GIO TLS backend.
- `transport=60`: проверить сертификат сервера, hostname, цепочку CA и время. Проверку TLS не отключать.
- HTTP 401/403: авторизация отклонена или URL устарел; заново выбрать трек в клиенте.
- HTTP 404: проверить ресурс. Сама колонка должна достигать hostname и порта источника.
- TRANSITIONING без PLAYING: загрузка/декодирование не завершились; читать transport/http и pipeline в журнале.
- PCM RUNNING и продвижение позиции подтверждают работу тракта, но финальная проверка — слышимая музыка.

На проверенной прошивке предупреждения `libasound.so.2: no version information available` и ALSA про AES-параметры при выборе выхода не мешали слышимому воспроизведению. Они не являются причиной менять `/etc/asound.conf`.

## Голос и очередь

Проверить bt-proxy, `/tmp/btbus/socket`, отсутствие активного `org.bluez.service` после установки и наличие его `.disabled`. Произносить обращение «Алиса».

**Известное ограничение 0.1.1: голосовое переключение назад может воспроизвести предыдущий трек на колонке, оставив интерфейс Feishin/Symfonium на текущем.** Это воспроизведено владельцем в обоих клиентах. Вперёд приёмник запускает заранее переданный SetNextAVTransportURI; назад использует собственную историю. Приложения не обязаны применять произвольный предыдущий URI к своей очереди. В проверенном исходнике Feishin неизвестный URI не обновляет очередь. В AVTransport нет симметричного SetPreviousAVTransportURI. Исправление синхронизации только в приёмнике не заявляется и в релиз не включено. Для синхронного перехода назад использовать кнопку в приложении.

`Дальше` требует переданного следующего URI: приёмник не имеет всей очереди приложения. Next/Previous на уровне UPnP и MPRIS тестировались отдельно; это не означает синхронизацию интерфейса клиента.

## Данные для диагностики

Записать модель, прошивку, версии YaDLNA и клиента, конкретное действие и краткий журнал. Перед публикацией убрать auth-URL, токены, аккаунты и идентификаторы. Не публиковать `/data/quasar`, дампы прошивки или музыку.
